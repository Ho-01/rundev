# 0041. 네이티브 샘플러와 크래시 진단 안전성

- 상태: Accepted
- 날짜: 2026-08-26

## 맥락

장시간 실행하거나 절전에서 복귀한 뒤 Windows에서 `STATUS_HEAP_CORRUPTION`,
macOS에서 원인 없는 프로세스 종료가 반복됐다. 기존 `battery 0.7.8`은 두 플랫폼에서
오래된 unsafe FFI를 사용하며 RunDev는 15초마다 manager를 새로 만들었다. 트레이
애니메이션도 창이 닫힌 동안 170ms마다 네이티브 아이콘을 교체했다.

기존 JSONL 진단 로그는 시작과 일부 상태 변경만 기록하므로 종료 시각과 마지막으로
정상 동작한 서브시스템을 구분할 수 없었다. 전체 메모리 덤프는 인증정보나 사용자
데이터가 포함될 가능성이 있어 RunDev의 개인정보 원칙에 맞지 않는다.

## 결정

- `battery` 크레이트를 제거한다.
- Windows 배터리는 할당 없는 `GetSystemPowerStatus`로 읽는다.
- macOS 배터리는 별도 `pmset -g batt` 프로세스의 집계 출력만 파싱한다.
- 숨겨진 트레이 팝오버에서는 애니메이션 갱신 간격을 낮추고, 긴 wall-clock 공백 뒤
  첫 네이티브 아이콘 교체를 건너뛴다.
- 앱은 로컬 runtime state에 시작 시각, PID, 버전, heartbeat와 각 서브시스템의 마지막
  성공 경과 시간만 기록한다. 정상 종료 시 clean 상태로 바꾼다.
- 다음 시작에서 이전 state가 running이면 `previous_run_unclean` 이벤트를 남긴다.
- Windows 치명 예외에는 `MiniDumpFilterMemory`와 `MiniDumpWithoutOptionalData`를
  사용한 필터 덤프만 로컬 diagnostics 폴더에 남긴다. 전체 메모리, 키 입력, 창 제목,
  파일 경로, 프롬프트, 응답은 수집하지 않는다.
- 크래시 파일은 자동 전송하지 않고 최근 2개만 유지한다.
- macOS에서는 운영체제가 만드는 `.ips` 보고서를 사용하며 RunDev는 해당 메모리
  내용을 복제하거나 자동 전송하지 않는다.

## 결과

### 장점

- 장시간 반복되는 구형 in-process 배터리 FFI를 제거한다.
- 비정상 종료가 발생한 시간대와 마지막 정상 서브시스템을 다음 실행에서 확인할 수 있다.
- Windows에서는 전체 메모리 없이도 네이티브 스택과 모듈을 분석할 수 있다.
- 기존 로컬 우선·최소 수집 원칙을 유지한다.

### 단점

- macOS 배터리 조회마다 짧은 `pmset` 프로세스가 실행된다.
- 힙이 이미 심하게 손상된 경우 Windows 필터 덤프 생성도 실패할 수 있다.
- 운영체제 강제 종료와 전원 차단도 unclean 종료로 분류되므로 crash와 완전히 같지는 않다.

## 대안

- 전체 메모리 덤프는 진단력은 높지만 비밀정보가 포함될 수 있어 제외했다.
- 기존 `battery` manager를 장기 재사용하는 방식은 절전 후 stale IOKit/SetupAPI 자원
  위험을 다시 만들기 때문에 제외했다.
- 배터리 표시를 완전히 제거하는 방안은 제품 메트릭 패널의 기능을 훼손해 제외했다.
